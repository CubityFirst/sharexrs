## Naming and evidence

- Write `G:/scripts/sharexrs-ref/shots/sharex/<area>/<id>-<dark|light>.png` and an adjacent `<id>-<dark|light>.json`. A row ID plus each backticked state gives a concrete ID, for example `tools-video/video-player-paused-dark.png`. **Both** means dark and light for each listed state. **D** and **L** request only that theme. Existing references are relative to `shots/sharex` and stay in place. Record approved captures and blocked states against their IDs in this manifest as batches land.
- The UIA column lists the controls to prioritize. In every sidecar record the reference commit, fixture, exact entry and state, theme/accent/density/locale, DPI and monitor work area, client origin and size in physical pixels, and relevant UIA control type, Name, AutomationId, displayed text/value, enabled/selected/toggled/expanded state and rectangle. Store rectangles in screen pixels and client-relative pixels. For custom-drawn previews, charts and overlays, record measured bounds and visible labels where UIA has no peer. For scroll shots record viewport, first and last visible card, and scroll percentage/offset when exposed. Use English with the existing 100% scale and default accent/density where available, and record any deviation.
- `winshot.ps1` uses client PrintWindow. For popup states also capture the ShareX-owned popup HWND using its position, size and z-order from `winrects.ps1` and the empty-title index in `winshot.ps1`. Put offsets/ownership in the JSON, retain individual captures under IDs ending in `-popup0`, `-popup1` as needed, and composite offline when needed for `scripts/compare.py`. A popup extending beyond the client keeps its own PNG. `uia.ps1 -Dump` gives names/types/IDs. Read bounds and state through the same process-scoped UIA elements, since the stock dump omits them. Use `input.ps1` for hover, scroll, and pointer-down snapshots. Release without invoking a command by moving off the control first. Use these interaction shots where a view has a distinct visual state, with one representative instance per shared style.
- Paths in the tables are relative to the upstream source root. `SX` means `ShareX/Presentation`, `Tools` means `ShareX.Tools/Tools`, `Helpers` means `ShareX.HelpersLib/Presentation`, and `Dest` means `ShareX.UploadersLib/Presentation/DestinationSettings`. Tools menu routes come from `SX/MainWindow/MainMenuBuilder.BuildToolCategories`, with command routing checked against `ShareX/ShareXCLIManager.cs` and `TaskHelpers.ExecuteJob`. A CLI name with a file denotes a verified file-taking job. Menu paths are preferred when the CLI job does something different.

## Phase 2 prerequisites and fixtures

- Wait for the handoff. Verify the exact portable executable and the portable profile routing (`ShareX/Infrastructure/PersonalPathManager.cs` gives the portable marker precedence over the configured personal folder). Scope every window operation to the reference PID. The name-based scripts require an unambiguous ShareX process or a PID-scoped wrapper. If the active instance cannot be verified, leave the desktop untouched. Back up the portable profile before changing any setting and start from a generated profile. Set `AutoCheckUpdate=false` before startup, clear unrelated startup integrations/watchers and credentials, and set after-capture jobs to local save/copy only except for the local test prompts specified below. Exit with `ShareX.exe -ExitShareX` before restoring the backup because ShareX saves on exit. Stop by PID only if needed, and only a process started for the capture batch. Leave Documents/ShareX untouched.
- **P** is a generated 640×400 checker/colour PNG, another with alpha, a 1600×1000 version for zoom, and a metadata-bearing JPEG made with generated EXIF/IPTC/XMP. Use the repository's image fixture generators where helpful. **V** is a local 8-second 320×180 H.264 MP4 with a synthetic tone and numbered frames, an invalid media file, three same-size numbered PNG frames and a looping three-frame GIF with unequal delays. Generate with offline tooling and use a locally available FFmpeg binary for converter, thumbnailer and trim export. **F** is a scratch tree with generated ASCII/Unicode text, duplicate/different byte files, a nested directory and a tiny CSS file, plus generated invalid input where requested. **H** is the repository's generated history fixture or local captures with synthetic titles and `example.invalid` placeholder URLs displayed as text. **C** is an empty or replaced clipboard with generated text, image and file-drop paths from P/F. Use a disposable clipboard context and skip when the original clipboard cannot be protected without exposing its contents. **T** is ShareXrs `--test-pattern`, covering every monitor with only safe targets available to screen-picking tools. Use a windowed, uniquely titled pattern for window enumeration and toggles. **D0** is a generated UploadersConfig with empty credentials, optional synthetic cached/local values and no live endpoints. Use generated fixtures and scratch output files throughout.
- Keep external network, loopback requests, uploads, browsers, sign-ins, keys, system integration/installers, UAC, Photo editor, Pixel editor and the system print dialog out of the session. Use native file pickers only if their initial folder and visible contents are known to be synthetic, with the shell's recent/pinned locations out of view. Capture only verified ShareX-owned client/popup HWNDs. Shell or picker UI with personal paths, enumerated third-party windows, logs with personal paths and unsafe overlay frames are excluded. Use full-monitor T coverage before opening screen or transparency tools. Run the existing pattern guard where applicable and delete uncertain frames unviewed. Pattern coverage alone cannot certify that a foreground window or overlay list contains safe data.
- **Conditional** means a local fixture, sanitized session, or capability must be verified before trying the route. **Blocked** means the target state has no safe route through the specified stock executable under the current rules. Where useful, the table identifies what a future in-process view fixture could supply without a network or writes to system state. Such a fixture would require separate scope and separate provenance from a shot of the portable executable.

## Destination settings (`destination`)

Use the sidebar/tray Destination settings window and search for the service page. The implementation is in `Dest/DestinationSettingsWindow`, `DestinationSettingsAccounts` and `DestinationSettingsPageBuilder`.
